## Target Architecture

The target data flow is:

Approved source register
→ optional acquisition and raw checksum verification
→ committed normalized edition
→ canonical structural passages
→ retrieval chunks for a named chunker configuration
→ index and ranked retrieval
→ passage-anchored benchmark
→ chunk relevance derived for the selected chunker
→ blinded review and reconciliation
→ development experiments
→ one held-out release run
→ report and interactive local answer experience

Key separation:

- Acquisition may require network access; CI does not.
- Normalized approved texts are committed public inputs.
- Raw downloads remain ignored cache material.
- Offline ingest rebuilds canonical passages and chunks from committed normalized texts.
- Questions cite canonical passages, not retrieval chunks.
- The review agent receives only a blinded bundle, never control labels.
- The optional local generator does not become a CI dependency.

## Contract Decisions the Executor Must Not Reopen

### Artifact-specific versions

Replace the assumption that one global schema number describes every artifact. Preserve v1 validators for v0.2. Add distinct versions for source register, pack, canonical passage, corpus or chunk, question, review request, review result, reconciliation, and run metadata.

### Canonical passage contract

Each passage includes:

- stable passage ID based on edition structure rather than global list position;
- source ID, author, work, translator, and edition;
- structural locator hierarchy such as book, chapter, section, proposition, treatise, song, or paragraph;
- content kind such as primary text, verse, translator note, historical editorial material, or excluded wrapper;
- exact normalized-text location and checksum;
- passage text checksum;
- predecessor and successor identities where applicable.

If corrected text changes under the same structural locator, the passage ID may remain recognizable but its checksum changes and dependent reviews become stale.

### Chunk contract

Each chunk includes:

- chunker ID and configuration checksum;
- stable source and passage membership;
- first and last passage ID;
- text and text checksum;
- source, author, work, translator, structural breadcrumb, and content-kind metadata;
- deterministic identifier unaffected by adding an unrelated source.

Chunks never mix primary and unapproved editorial content. Oversized passages are split through a deterministic documented fallback.

### Question contract version 2

Each question includes:

- question ID and family ID;
- primary task type and risk tags;
- answerability: answerable, unanswerable, or excluded-pending-adjudication;
- one or more acceptable evidence sets for answerable questions;
- required evidence groups inside a set for multi-hop questions;
- canonical passage references, never only chunk references;
- concept or evidence-cluster identity used for split grouping;
- development or held-out split after freeze;
- curation and review state.

Unanswerable questions have no supporting evidence set. They instead contain a documented corpus-scope rationale in the hidden control record.

### Review contracts

The blinded request records approved input files, opaque IDs, randomization seed, protocol and artifact checksums, review kind, declared independence level, and whether external context is authorized.

The public review result records reviewer type and model identity when available, protocol version, input checksum, independence level, external-context disclosure, structured verdicts, reason codes, confidence, selected evidence, and escalation status. It contains concise evidence-bound rationale, not hidden chain-of-thought.

The reconciliation record is a separate artifact. The reviewer never edits questions, chunks, passages, labels, manifests, or gold data.

## Phase 8 — Retrieval Evaluation and Model Experiments

### Goal

Establish honest v0.3 baselines, diagnose failures, and admit complexity only when measured.

### Deterministic baselines

- Keyword.
- BM25.
- TF-IDF cosine under an unambiguous v0.3 method ID.
- BM25 plus TF-IDF reciprocal-rank fusion.

### Optional local experiments

- One local dense embedding model, only if its runtime is available or can be installed with approval.
- One local reranker only if development traces show ranking, rather than recall, is the bottleneck.
- Existing untracked embedding output is not reused as canonical evidence.
- Every optional run records model name, version or digest, dimensions, normalization, runtime profile, and checksums.

### Methodology

1. Run end-to-end development traces first and classify retrieval versus generation failures.
2. Choose primary k values on development by task type.
3. Optimize first-pass retrieval for recall.
4. Evaluate reranking through precision, MRR, or nDCG only after recall is adequate.
5. Report complete-evidence success for multi-hop tasks.
6. Report results by source, work, task type, answerability, and risk tag.
7. Establish v0.3 regression floors from repeatable development results only after the pipeline is frozen.
8. Run the held-out test once for the release candidate.
9. Use paired per-question uncertainty when comparing methods and avoid declaring a universal winner when intervals overlap.

### Gate 8

- Development and held-out artifacts are distinct and checksum-bound.
- Unanswerable questions are excluded from ordinary retrieval recall calculations.
- Multi-hop partial evidence does not count as complete success.
- Actual method labels match actual algorithms.
- New regression floors are supported by recorded v0.3 runs.
- The held-out run is not used to retune the system.
- Any claimed improvement names the corpus, dataset, metric, k, baseline, uncertainty, and limitations.

## Stop and Escalation Conditions

Stop the affected phase and report instead of guessing when:

- a translation or edition does not match the approved source;
- a rights or license conflict appears;
- a normalized source cannot be traced to the authoritative edition;
- an original scan and transcription materially disagree;
- a question depends on Greek or Latin, chronology, authorship, or contested doctrine;
- the only way to proceed is to inspect or ingest a user-owned modern book;
- the held-out set has been exposed during tuning;
- the reviewer has seen control labels;
- v0.2 behavior would need destructive migration;
- implementation requires a cloud service or external write outside the approved scope;
- a destructive git or filesystem action appears necessary;
- release or publication authority is needed.

When a source or item is blocked:

1. Preserve the failure evidence.
2. Mark the artifact blocked or excluded.
3. Return to the last passing gate.
4. Continue only independent safe work.
5. Do not replace the work, weaken the gate, or claim full completion.
